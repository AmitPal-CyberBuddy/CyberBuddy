How it scores

Methodology

Four read-only checks, the same graders in Python and in the browser, and report cards you can paste into an assessment. Authorized testing only.

What each tool proves

Clickjacking Validator

Reads X-Frame-Options and CSP frame-ancestors, then loads the target in a live iframe. If the real UI appears, the page can be framed in this browser — that is the proof, not just the headers.

OWASP WSTG-CLNT-09 · CWE-1021

Security Headers

Grades ten header families on a 0–100 scale (A–F). Every finding shows the raw value it used. Cookie flags are checked when Set-Cookie is present.

OWASP WSTG-CONF-07 / CONF-12 · CWE-693

CORS Validator

The Python engine probes two fake origins to prove reflection vs an allowlist. On GitHub Pages, the browser can only speak as github.io — a single-origin probe, marked honestly.

OWASP WSTG-CLNT-07 · CWE-942

CSP Policy Auditor

Distinguishes enforced CSP from Report-Only, resolves effective script/style fallbacks, and audits object, base, framing, form, mixed-content, syntax, Trusted Types, and reporting controls.

OWASP WSTG-CONF-12 · CWE-79 · CWE-693

What it does not do

No exploits, no authenticated sessions, no POST/PUT/DELETE. Results are advisory. A green grade is not a guarantee of safety and a red grade is not a CVE.

Grade bands: A ≥ 90 · B ≥ 75 · C ≥ 60 · D ≥ 45 · F below that. Risk follows the grade (A/B low, C/D medium, F high).

CSP risk

There is no CSP /100 score. The highest-confidence actionable finding sets the risk. Multiple enforced CSP headers combine restrictively, and later duplicate directives inside one policy are ignored by browsers.

How the hosted site scans

01 · Python engine

When server.py or a hosted api/ is reachable, every check uses the same stdlib engines as the CLI — including two-origin CORS.

02 · Published report

GitHub Actions pre-scans the demo targets in urls.txt every six hours and publishes them as cache/<host>.json. Fresh reports (under 48 hours) are served same-origin and labelled via published report. These cover the demo targets only — your scans are never uploaded or cached server-side.

03 · Direct, then relay

The browser first tries to read the target directly (works only when the target sends permissive CORS — no third party involved). If that fails, header reads can be proxied by public relays, but only after you agree. CORS is probed from this origin only. The source chip always names the layer that ran.

Privacy — what leaves your browser

Scan history is local. Recent targets and the 10-minute header cache live in this browser's localStorage and expire after 24 hours. They are never uploaded, never shared between users, and are not visible to anyone else. Clear on the hub wipes both the recent list and the cached response headers immediately.

Published reports are not your scans. cache/<host>.json is built in CI from the fixed demo list in urls.txt. Nothing a visitor types is ever written there.

Third-party relays are opt-in. Browsers cannot read cross-origin response headers, so with no Python engine available the hosted site must proxy the request. That discloses the target — and your IP — to the relay operator, which many assessment NDAs prohibit. So CyberBuddy asks first, defaults to sending only the hostname (not the path or query string, which is where tokens and tenant IDs live), and marks anything a relay returns as unverified. Relays used: hackertarget.com, allorigins.win, corsproxy.io, codetabs.com.

For a scan where nothing leaves your machine, run python3 server.py locally — the same graders, same-origin, no relays.

Authorized testing

You may only point CyberBuddy at systems you own or have written permission to assess. The hosted cache only includes IANA documentation hosts (example.com, example.org, example.net) and this project’s own GitHub Pages origin. Cloud-metadata and link-local addresses are always refused. Private RFC1918 targets are allowed only when server.py is loopback-bound (or you pass --allow-private).
