How it scores

Methodology

Four non-destructive HTTP assessment tools, one public-DNS analyzer, and two local security utilities (CSRF PoC Generator and JWT Security Workbench) — with transparent scoring and report cards you can paste into an assessment. Authorized testing only.

What each tool proves

Clickjacking Validator

Reads X-Frame-Options and CSP frame-ancestors, then loads the target in a live iframe. If the real UI appears, the page can be framed in this browser — that is the proof, not just the headers.

OWASP WSTG-CLNT-09 · CWE-1021

Security Headers

Grades ten header families on a 0–100 scale (A–F). Every finding shows the raw value it used. Cookie flags are checked when Set-Cookie is present.

OWASP WSTG-CONF-07 / CONF-12 · CWE-693

CORS Validator

GET is the baseline read-only probe. The Python engine sends two fake Origins (evil.cyberbuddy.test, probe.cyberbuddy.test) plus Origin: null to prove reflection vs allowlist and the null-origin bypass — for every selected method. Additional coverage is analyst-selected for an authorized endpoint: HEAD (direct), OPTIONS (direct), and a preflight simulation (OPTIONS + Origin + Access-Control-Request-Method: POST and optional Access-Control-Request-Headers) without sending a POST body. Unsupported methods (HTTP 405/501) are reported as not assessed, never as safe. A global “CORS PASS” is never shown when only GET was examined — the report shows a coverage matrix and the highest primary risk across all successfully assessed methods.

OWASP WSTG-CLNT-07 · CWE-942

CSP Policy Auditor

Distinguishes enforced CSP from Report-Only, resolves effective script/style fallbacks, and audits object, base, framing, form, mixed-content, syntax, Trusted Types, and reporting controls.

OWASP WSTG-CONF-12 · CWE-79 · CWE-693

CSRF PoC Generator

Parses a pasted Burp request and rebuilds it as standalone HTML — forms for GET/POST, fetch() for JSON and non-form methods — each labelled READY, LIMITED, or NOT DIRECTLY REPRESENTABLE by browser mechanics. It runs entirely in your browser, never sends or stores the request, and never executes the PoC.

OWASP WSTG-SESS-05 · CWE-352

JWT Security Workbench

Decodes, inspects, and cryptographically verifies JSON Web Tokens locally using Web Crypto API (HMAC, RSA-PKCS#1, RSA-PSS, ECDSA). Generates authorized-test variant templates (alg:none, RSA-to-HMAC key confusion, embedded JWK, header URL, kid traversal) and runs offline HMAC dictionary tests in a dedicated Web Worker. Decoding also surfaces prioritized, severity-tagged VAPT testing suggestions with one-click TEST PAYLOADs and Burp Suite verification steps. Zero external network calls.

OWASP WSTG-SESS-10 · RFC 7519 · CWE-347

DNS & Domain Security Analyzer

Reads a domain's public DNS records — SPF, DMARC, DKIM, DNSSEC, CAA, MX and name servers — through a resolver (your system resolver locally, or DNS-over-HTTPS on the hosted site after consent). It never connects to the domain's own servers. Each finding shows the raw record value it used; a missing DKIM key on common selectors is labelled as a hint, not proof of absence.

RFC 7489 · RFC 7208 · RFC 6376 · RFC 4033 · CWE-290

What it does not do

No exploits, no authenticated sessions, no POST/PUT/DELETE sent to a target — the CORS Validator never automatically sends POST (including empty-body POSTs); preflight is simulated with OPTIONS only. The CSRF and JWT tools run strictly in your browser and never transmit tokens, requests, or key material to any server or third party. Results are advisory. A green grade is not a guarantee of safety and a red grade is not a CVE.

No reflection, no wildcard misuse (fixed allowlist or no CORS headers)Low — “No risky CORS behavior observed for GET” when only GET was tested; complete coverage matrix shown

Risk is evaluated per tested response/method (GET, HEAD, OPTIONS, preflight POST, etc.) and the report rolls up the highest observed primary risk. Origin: null is probed for every selected method that can accept an Origin header. The analyst must be authorized for the target endpoint, which may not support every method. GET-only coverage never implies every method is safe. Browser probes on GitHub Pages are single-origin (cannot forge Origin, cannot set Access-Control-Request-Method/Headers or inspect automatic preflight); they identify actual methods attempted and state that python3 server.py is required for two-origin/null/preflight proof. Identical scoring semantics are preserved for equivalent observed inputs; capability limits are documented, not faked.

How the hosted site scans

01 · Python engine

When server.py or a hosted api/ is reachable, every check uses the same stdlib engines as the CLI — including two-origin and null-origin CORS probes for every selected method (GET baseline + analyst-selected HEAD, OPTIONS, and preflight POST with optional headers). POST is never sent automatically.

02 · Published report

GitHub Actions pre-scans the demo targets in urls.txt every six hours and publishes them as cache/<host>.json. Fresh reports (under 48 hours) are served same-origin and labelled via published report. These cover the demo targets only — your scans are never uploaded or cached server-side.

03 · Direct, then relay

The browser first tries to read the target directly (works only when the target sends permissive CORS — no third party involved). If that fails, header reads can be proxied by public relays, but only after you agree. CORS is probed from this origin only for the methods you select (GET baseline + HEAD/OPTIONS where browser CORS permits); preflight cannot be manually set or inspected in browser JS, and the report states that python3 server.py is required for two-origin/null/preflight proof. The source chip always names the layer that ran and the coverage matrix lists tested vs unassessed methods.

04 · DNS via resolver

The DNS & Domain Security Analyzer reads public DNS through your system resolver when the Python engine is reachable, or a consent-gated DNS-over-HTTPS lookup (dns.google) on the hosted site. There is no cached DNS layer, and the target's own servers are never contacted.

Privacy — what leaves your browser

Scan history is local. Recent targets and the 10-minute header cache live in this browser's localStorage and expire after 24 hours. They are never uploaded, never shared between users, and are not visible to anyone else. Clear on the hub wipes both the recent list and the cached response headers immediately.

Published reports are not your scans. cache/<host>.json is built in CI from the fixed demo list in urls.txt. Nothing a visitor types is ever written there.

Third-party relays are opt-in. Browsers cannot read cross-origin response headers, so with no Python engine available the hosted site must proxy the request. That discloses the target — and your IP — to the relay operator, which many assessment NDAs prohibit. So CyberBuddy asks first, defaults to sending only the hostname (not the path or query string, which is where tokens and tenant IDs live), and marks anything a relay returns as unverified. Relays used: hackertarget.com, allorigins.win, corsproxy.io, codetabs.com. After consent, the hosted fallback also sends the hostname to dns.google for A/AAAA lookup. This lets CyberBuddy identify NXDOMAIN and domains with no web address instead of presenting a misleading security grade.

The DNS analyzer reads public DNS only. It queries a resolver (your system resolver locally, or dns.google after consent on the hosted site) and never connects to the target's own servers. The only disclosure on the hosted path is the domain name (plus its parent labels queried for inherited CAA) and your IP to Google Public DNS; records returned this way are labelled unverified.

To avoid disclosing a target to header relays or Google Public DNS, run python3 server.py locally — the same graders, same-origin, and no CyberBuddy relay or storage. HTTP scans still contact the target, and DNS analysis still uses your configured resolver.

Authorized testing

You may only point CyberBuddy at systems you own or have written permission to assess. The hosted cache only includes IANA documentation hosts (example.com, example.org, example.net) and this project’s own GitHub Pages origin. Cloud-metadata and link-local addresses are always refused. Private RFC1918 targets are allowed only when server.py is loopback-bound (or you pass --allow-private).
