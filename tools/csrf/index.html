Tool 05

CSRF PoC Generator

Paste a raw Burp HTTP request and get a standalone HTML proof-of-concept for authorized CSRF testing. Everything runs locally in this browser.

Aligned with OWASP WSTG-SESS-05 · CWE-352

New to this check? Read the 5-minute CSRF guide first.

Paste from Burp Repeater · Local only. The request is parsed and turned into a PoC in this tab — it is never sent, stored, cached, relayed, or placed in the URL. The PoC is shown as inert text below and only leaves this page when you download or copy it. Cookie, Authorization, Host, Content-Length, Origin and Referer values are never copied into the PoC — the victim’s own ambient cookies are used instead.

Auto-submit is on. The downloaded PoC will send the request the moment it is opened, which can change state on the target. Only use it with a throwaway, authorized test account.

ℹ What this generator does — and does not do

CyberBuddy parses the request line, headers, query string and body, then rebuilds it as one or more standalone HTML pages using only what a browser can actually send: HTML forms for GET/POST and fetch() for everything else. Each variant is labelled READY (a simple request, no preflight), LIMITED (depends on a CORS preflight or server leniency), or NOT DIRECTLY REPRESENTABLE (no browser mechanism reproduces it).

Pasted request→Local parse→Honest HTML PoC

A generated PoC reproduces request mechanics, never a vulnerability verdict. The target must also change state, accept the request cross-site, and rely on the victim’s ambient credentials. File fields cannot be pre-populated, and exact application/json bodies cannot be sent by a plain form — CyberBuddy says so instead of pretending otherwise.

Prerequisites

  • State-changing endpoint — the request must actually change state.
  • Ambient credentials — the victim is logged in and the browser attaches their cookies.
  • No effective token — the target must not reject the request via a CSRF token the PoC cannot supply.
  • SameSite cookies — cookies marked SameSite=Lax/Strict are not attached to most cross-site requests.
  • Origin / Referer checks — the target must not require an Origin or Referer the attacker page cannot produce.
  • Simple request vs preflight — LIMITED variants need the CORS preflight answered.
  • Re-authentication — sensitive flows that demand a fresh login cannot be crossed.

How to test

  1. Use a dedicated, authorized test account you are permitted to mutate.
  2. Host the downloaded PoC on a separate origin from the target (a different domain, or a localhost server).
  3. Open the PoC in a browser where the test account is logged in.
  4. Check whether the state change actually occurred; if not, note which control blocked it.
  5. Never run it against other users or production accounts.

Recommendations

    ! ! Authorized testing only. Generate PoCs for systems you own or have written permission to assess. A generated PoC reproduces request mechanics — it never proves the target is vulnerable, and it never executes inside CyberBuddy.
