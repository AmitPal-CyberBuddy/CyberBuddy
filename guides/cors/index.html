CORS: when sharing becomes reading

CORS exists to relax the same-origin policy on purpose. The bug is almost never the relaxation itself — it is who gets included in it, and whether the response carries a session.

Aligned with OWASP WSTG-CLNT-07 · CWE-942 — permissive cross-domain policy

Open the CORS Validator

The attack in one paragraph

A victim who is logged into your API visits a page the attacker controls. That page issues a cross-origin fetch() to your endpoint with credentials. The browser sends the victim's cookies and then checks the response: if Access-Control-Allow-Origin names the attacker's origin and Access-Control-Allow-Credentials: true is present, the attacker's JavaScript is allowed to read the authenticated response body. No injection, no stolen token — the browser hands the data over because the server said it was fine. Note the direction: CORS governs reading responses, so a permissive policy is a disclosure bug, and it is not a CSRF defence either way.

How servers get it wrong

PatternWhy it happensImpact
Reflected Origin The server echoes whatever Origin arrived, because an allowlist was “too much work”. With credentials, full read of authenticated responses. Without, still an unintended trust boundary.
Sloppy allowlist match A prefix or suffix check instead of an exact comparison, or a regex where the dot was never escaped. evil-normal-website.com or normal-website.com.attacker.net passes the check.
Allowlisted null Someone added it to make local files or redirects work. Any attacker can produce a null origin from a sandboxed iframe or a data: URL.
Wildcard with credentials Copied from a tutorial. Invalid — browsers reject the combination — but it signals the policy was never designed.
Missing Vary: Origin Per-origin headers behind a shared cache. A CDN can serve one caller's Access-Control-Allow-Origin to another.

One more thing worth knowing before you argue with a developer: Origin is a forbidden header name, so page JavaScript cannot forge it — but curl, Burp and any non-browser client set it to whatever they like. It is a browser-enforced hint, never an authentication signal.

Confirm it with the validator

  1. Open the CORS Validator and paste an endpoint you are authorized to test — an API path, not the marketing homepage.
  2. Press Probe. It sends two read-only GETs with two different attacker origins.
  3. Compare the two Access-Control-Allow-Origin values. Both echoed back means arbitrary reflection, and two distinct probes rule out a coincidental allowlist hit.
  4. Check Access-Control-Allow-Credentials. That flag is what turns a permissive policy into readable authenticated data.
  5. Export the report card — it carries both probe origins, the raw headers, the final URL, the status and the timestamp.

The risk it prints follows the observed outcome: reflection with credentials is High; reflection alone, or a wildcard alongside credentials, is Medium; a wildcard without credentials or a fixed Access-Control-Allow-Origin is Low. Vary: Origin is reported as its own finding and never sets the headline risk — it is a cache-hardening issue, not an access one. The full table is on the methodology page.

The fix

Keep a server-side allowlist, compare the Origin value for exact equality, and only then echo it back: 

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin

No wildcards, no null, no substring or regex matching, and no credentials on an endpoint that does not need them. If the data is genuinely public, drop credentials entirely and Access-Control-Allow-Origin: * is fine. Then re-probe: a correctly configured endpoint returns your allowlisted origin regardless of what the two probes claimed to be.
