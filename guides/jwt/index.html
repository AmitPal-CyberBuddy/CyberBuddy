JWT: decode, verify, and the surfaces that matter

A JSON Web Token is three base64url segments — header, payload, signature. Most confusion in a JWT assessment comes from treating the first two as if they were the third: decoding tells you what a token claims, verification tells you whether to believe it.

Aligned with RFC 7519 · RFC 7515 · OWASP WSTG-SESS-10 · CWE-347

The Workbench decodes, verifies, signs and tests today. Everything at the JWT Workbench runs locally in your browser. Every output is a TEST TOKEN or TEST TEMPLATE until the target actually honors it.

Header, payload, signature

The header names the algorithm (alg) and key id (kid); the payload carries the claims — issuer, subject, audience and the time claims; the signature is the only part tied to a key. The first two are base64url, not encryption, so a secret in a claim is exposed. I keep three states sharp in the UI: Decoded is free; Signature verified means a key you supplied matched; Claims validated means the expected issuer, audience and lifetime also hold.

Decoding is not verification

You can decode any well-formed JWT without a key; that shows the claims and declared algorithm, but says nothing about whether the signature is valid. A token that decodes cleanly can still be unsigned, tampered with, or signed by a key the target does not trust — decoding is reconnaissance, not a result. A valid signature with a key you supplied proves only a match with that key, not that it is the key the target uses. The Verify tab says so plainly.

Time claims: iat, nbf, exp

ClaimMeans
iatIssued-at time.
nbfNot valid before this time.
expExpiry; accepted only before it.

Clock skew between issuer and verifier is real, so the Workbench exposes a skew setting instead of ignoring it. A long lifetime widens the replay window if a token leaks. Missing exp is worth noting, but contextual — some tokens are intentionally long-lived.

Issuer and audience

iss names who issued the token; aud names who it is for. A service that accepts a token minted for a different audience trusts a token it was never meant to receive. The Workbench lets you state the expected issuer/audience/subject and reports mismatches as claims findings, separate from the signature.

Symmetric vs asymmetric

HMAC (HS256/384/512) signs and verifies with a shared secret. RSA and EC (RS256, PS256, ES256) sign with a private key and verify with a public key. The Workbench uses the native Web Crypto API — PEM, JWK or a pasted JWKS to verify, a secret or private key to sign. No key leaves the browser.

The attack surfaces I actually test

SurfaceWhat to look for
alg: noneA server that accepts an unsigned token after stripping the signature.
Algorithm confusionA token HMAC-signed with the victim's public key as the secret — possible only when the verifier treats a public key as a shared secret.
kidKey-id pulled into a file path or SQL query; traversal or injection can choose the verifying key.
jku / x5uHeader URLs pointing at a key set; fetched without strict allowlisting, an attacker URL supplies the key.
Embedded jwkA token carrying its own public key in the header and asking the server to trust it.

Presence is not proof. A kid, jku or embedded JWK is an attack surface, not an exploited vulnerability; confusion stays potential until the server accepts it — test templates, never findings.

HS256 is not automatically weak. A strong high-entropy secret over HTTPS is reasonable; the weakness is a guessable or leaked secret, not the algorithm. Secret testing stays bounded — HS256/384/512 only, a small built-in list plus your wordlist, in a Web Worker with progress and cancel — and never persists anything.

Replay and lifetime

A signature proves integrity and authenticity at issue time, not that the token is still okay to use; a stolen but unexpired token is valid. Short lifetimes, rotation, and a revocable jti bound the replay window. An exp you read from a decoded token does not prove the server enforces it — that is what you test.

What the Workbench will and won't do

Every panel is fully functional. The Workbench decodes a compact JWS into header, payload, signature and a claim timeline, lists contextual observations, verifies HMAC, RSA-PKCS#1, RSA-PSS and ECDSA signatures, re-signs edited claims with a key you supply or generate, builds labelled test-variant templates, and runs bounded HS256/384/512 secret testing in a Web Worker — all via Web Crypto. Decoding yields prioritized VAPT suggestions with one-click TEST PAYLOADs (alg:none, RS→HS confusion, embedded JWK, kid, jku/x5u, claim tampering) for manual proxy verification. It never trusts the token's alg header to choose the verifier, and HMAC rejects public keys.

Generating a modified token proves you can build the bytes, not that the server accepts it — every output is a TEST TOKEN or TEST TEMPLATE. The hosted tool never sends a JWT to a target, JWKS URL or third party.

Remediation checklist

  • Pin accepted algorithms server-side; never let the token's alg header choose the verifier.
  • Reject alg: none unless unsigned tokens are an explicit requirement.
  • Verify exp, nbf, iss and aud every request, with bounded skew.
  • Use strong, rotated keys — high-entropy HMAC secrets or adequate RSA/EC keys.
  • Validate kid against an allowlist; never use it as a file path or unescaped query.
  • Never fetch jku/x5u or trust an embedded jwk without pinning.
  • Keep lifetimes short; support revocation via jti or a denylist.
  • Send tokens only over HTTPS; store them away from XSS reach.

Limitations

The Workbench is local; it cannot prove a server accepts a variant — only an authorized, observed request can. Large-scale cracking, OAuth/OIDC discovery and full JWE support are deferred. The methodology behind the other tools lives on the methodology page.
