CSRF: proving an action can be forged

Cross-site request forgery is not about stealing a session. It is about borrowing one. The browser attaches the victim's cookies to a request the victim never intended to make — and if nothing unpredictable is required, the action goes through.

Aligned with OWASP WSTG-SESS-05 · CWE-352 — cross-site request forgery

Three conditions, all required

ConditionWhat to check
An action worth forging It changes state or privilege: change email, add a payment method, promote a user, delete an object.
Session handled by the browser alone Cookies or HTTP Basic auth attached automatically. A bearer token that JavaScript must add is not automatically sent, so it breaks the attack.
No unpredictable parameter Every field in the request can be guessed by the attacker. One unguessable, validated anti-CSRF token kills it.

All three must hold. That is why the interesting part of a CSRF test is not finding a state-changing endpoint — it is proving that nothing in the request was unpredictable. And it is why re-testing after a fix is cheap: remove any one condition and the finding is closed.

Why the PoC is the finding

A triager can dismiss “this endpoint has no CSRF token” as theoretical. They cannot dismiss an HTML file that, opened in a logged-in browser, changes the account. For a GET action the whole exploit is a zero-size <img src>; for a form-encoded POST it is a hidden auto-submitting form. That file is the artifact I attach to the report, and it is the thing the developer runs to confirm the fix.

A subtlety worth stating in the write-up: form-based login does not make an application safe. Once a session cookie exists, the browser sends it with the forged request exactly as it would with a real one.

Build it with the generator

  1. Open the CSRF PoC Generator and paste the raw HTTP request, straight from Burp.
  2. Press Generate PoC. Everything runs in your browser — the tool never sends, executes, relays or stores the request.
  3. Read the status line before the HTML. It tells you whether a browser can actually reproduce the request.
  4. Download the PoC, open it in a session you are authorized to use, and confirm the action happens.
  5. Copy the Markdown assessment for the report; it pairs with the HTML file as the evidence.

The three statuses mean specific things:

  • READY — reproducible as a simple browser request with no preflight. This is a clean, self-contained proof.
  • LIMITED — reproducible, but with a caveat. An application/json body forces a CORS preflight from fetch(), so it only lands if the server also accepts text/plain; a multipart body with a file field needs the victim to pick a file. Say so in the report rather than overclaiming.
  • NOT DIRECTLY REPRESENTABLE — no browser mechanism reproduces this request, usually because of a custom header. That is itself a defence, and worth recording as one.

The risk the report card prints follows the status: READY is low friction and therefore the strongest claim; the mapping is on the methodology page.

The fix

Use the framework's built-in protection before writing your own. Where you must choose: a stateful app uses a synchronizer token bound to the session; a stateless one uses a double-submit cookie. Then add the cheap layers: 

Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax

Never perform state changes on GET. Treat SameSite as defence in depth, not the control — and remember that a cookie scoped to a parent domain is shared with every subdomain, so one weak subdomain undoes it. If the target is modern-browser only, Sec-Fetch-Site checking is a strong addition. One caveat that outranks all of the above: an XSS anywhere in the origin defeats every CSRF mitigation, because the attacker's script can simply read the token.
