Security headers: what the grade is actually measuring

A header scan is easy to run and easy to misread. A missing header is not automatically a finding, and a present one is not automatically a control. What matters is which headers carry weight, and what their values say.

Aligned with OWASP WSTG-CONF-07 / CONF-12 · CWE-693 — protection mechanism failure

Open the Security Headers scan

Why a header is a control

Response headers are the only security policy a browser applies before your JavaScript gets a vote. They decide whether a page can be framed, whether a script from another origin may run, whether the connection may silently fall back to HTTP, and whether a mistyped Content-Type gets guessed into something executable. None of them fix a vulnerability in the application — they narrow what an existing bug can reach, which is exactly why their absence maps to CWE-693, a protection mechanism that is missing, insufficient, or simply not applied on one code path.

That last case is the one I see most: the headers are right on /login and absent on /api, or present on the HTTPS response and missing from the HTTP redirect that got the user there. Scan more than the homepage.

What the score weighs

HeaderWeightWhat earns full marks
Content-Security-Policy 25 An enforced policy with a restrictive script source. Report-Only alone does not count.
X-Frame-Options 15 DENY or SAMEORIGIN. If CSP frame-ancestors already restricts framing, a missing value costs 5 instead of 15.
Strict-Transport-Security 15 max-age of at least 180 days plus includeSubDomains, on HTTPS only.
X-Content-Type-Options 10 nosniff. There is no other valid value.
Referrer-Policy 10 A policy that does not leak the full URL cross-origin — strict-origin-when-cross-origin is the sane default.
Permissions-Policy · COOP · COEP · CORP 5 each Present and meaningful. These are hardening, not headline findings.
Cookie flags 5 Session cookies carrying Secure, HttpOnly and a SameSite value.

Grades fall out of the remaining score: A at 90 or above, B at 75, C at 60, D at 45, F below that. A and B report low risk, C and D medium, F high. The weights and the full deduction table are on the methodology page.

The three I argue about most

HSTS. Without it, the first request to http:// is interceptable and the user can click through a certificate warning. max-age=31536000; includeSubDomains is the value to ask for. Two rules people get wrong: browsers ignore the header entirely when it arrives over plain HTTP, so it must not be on the redirect response — only on the HTTPS one that follows; and includeSubDomains does not cover the parent domain, so www.example.com still needs its own header.

X-Content-Type-Options. One value, nosniff, and it only helps if the Content-Type you send is correct and carries a charset. A JSON endpoint labelled text/html is a bug that nosniff will happily enforce.

X-XSS-Protection. Scanners still flag it as missing. OWASP recommends sending 0 — the legacy auditor it enables has itself introduced XSS on otherwise-safe pages. Do not treat its absence as a finding.

Confirm it with the scan

  1. Open the Security Headers tool and paste a URL you are authorized to test.
  2. Press Scan. It is a read-only GET; the grade is computed from the response headers alone.
  3. Read each finding's evidence line — it prints the raw header value that produced the verdict, which is what a developer will ask for.
  4. Re-scan an authenticated path and an API path, not just /. Header configuration is per-response, and that is where it diverges.
  5. Export the report card. It carries the target, final URL, HTTP status, timestamp and the engine that produced the result.

A deep dive on the CSP value itself belongs in the CSP guide; framing belongs in the clickjacking guide. This scan tells you which controls exist. Those two tell you whether they hold.

The fix

Set these at the edge, on every response, and let the app override only where it must:

Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Cache-Control: no-store

no-store only where responses are sensitive — no-cache does not prevent storage, it just forces revalidation. Then re-scan: the grade moves, and the report card is your before-and-after evidence.

Go deeper

I keep this short on purpose. When a value is disputed, these are the references I open:

  • OWASP HTTP Security Response Headers Cheat Sheet — recommended values header by header, including why X-XSS-Protection: 0 is the advice.
  • OWASP WSTG-CONF-07 — Test HTTP Strict Transport Security — the HSTS test procedure and directive detail.
  • CWE-693 — Protection Mechanism Failure — the identifier to cite; note it is a Pillar, so map to a more specific CWE when one fits.
  • MDN — Strict-Transport-Security and MDN — Referrer-Policy — exact syntax, defaults and expiry behavior.
  • MDN — Set-Cookie — what Secure, HttpOnly, SameSite and the cookie prefixes actually enforce.
