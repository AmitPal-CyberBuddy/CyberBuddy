Running the suite

Documentation

Everything you need to run CyberBuddy properly: the local server that unlocks full scans, the three engines and when each one answers, the command-line tools, and the evidence formats you attach to a report. Authorized testing only.

Python 3.10+ · no build step · no third-party packages

Quick start

The hosted site works on its own, but a local server is what gives you complete evidence — server-side header reads and the two-origin CORS proof a browser simply cannot perform. Clone the repo and run: 

python3 server.py
# open http://127.0.0.1:8080/

That serves the hub, every tool page, and the JSON APIs behind them. It binds 127.0.0.1 — loopback only — by default. Point your browser at the catalog at /tools/ and pick a check, or run the whole suite from the hub. Local utilities like the CSRF PoC Generator and JWT Security Workbench execute 100% in your browser (via Web Crypto) with zero network exposure.

To reach it from another machine on your network, bind wider. Private-IP targets stay refused unless you opt in explicitly, because scanning RFC1918 space is a decision you should have to make on purpose: 

python3 server.py --host 0.0.0.0
python3 server.py --host 0.0.0.0 --allow-private

Cloud-metadata and link-local addresses are always rejected, on every bind, with no flag to override. A PORT environment variable — the usual PaaS convention — switches the default bind to 0.0.0.0, so treat that as an explicit choice too.

Which engine answers

How scoring works →

Every report names the layer that produced it, and the engine chip in the header tells you which one is live before you scan. There are three, in order of preference:

01 · Python engine

When server.py or a hosted api/ is reachable, checks run server-side with the same stdlib engines as the CLI. Complete evidence, nothing relayed.

02 · Published report

Demo targets are pre-scanned in CI and served from cache/<host>.json. These are labelled CACHED, never LIVE, and cover the fixed demo list only.

03 · In-browser graders

The same scoring logic, ported to JavaScript. A direct cross-origin read is tried first; a public relay is used only if you approve it.

The grading rules themselves — score bands, risk levels, what each finding means — live on the methodology page. I keep them there rather than repeating them here so there is exactly one place to correct when they change.

Tools with no engine behind them

Two tools never touch any of the three layers above, because they never scan a target. The CSRF PoC Generator builds an HTML proof of concept from a request you describe. The JWT Security Workbench works entirely on a token you paste. Both run in the page itself, so there is no engine chip and no relay prompt — and nothing to leak.

What the Workbench does with a pasted token, in one place:

CapabilityHow it runs
Decode & inspect Strict compact-JWS parsing; header, payload and a claim timeline for iat, nbf and exp. Observations are reported in context, never as a score.
Verify a signature HMAC, RSA-PKCS#1, RSA-PSS and ECDSA through Web Crypto, using a key you supply. The token's own alg never selects the verifier, so algorithm confusion cannot pass silently.
Edit, generate & re-sign Header and payload editors with standard-claim helpers, a semantic diff of your changes, local RSA test-key generation, and signing that stamps every result a TEST TOKEN.
Test variants Templates for alg:none, claim tampering, algorithm confusion, embedded JWK, jku/x5u and kid injection — each labelled a TEST TEMPLATE until a target honors it.
Secret testing Bounded HS256/384/512 dictionary search in an isolated Web Worker, with live progress and cancel, so the interface stays responsive. A match is a secret you have recovered for your own testing — not a verdict about the target.

The Workbench will not send a token to a target, a JWKS URL or any third party. Confirming that a target actually accepts one of these tokens is a separate, deliberate step you take yourself against a system you are authorized to test.

Command line

Each engine is also a standalone CLI, which is what I reach for when I need to sweep a list of hosts rather than assess one target carefully: 

python3 clickjacking_validator.py https://example.com
python3 security_headers.py https://example.com
python3 security_headers.py -f urls.txt --json --workers 8
python3 cors_validator.py https://example.com/api
python3 csp_checker.py https://example.com --json

Add --public-only to refuse loopback and RFC1918 targets. Exit code 1 means at least one target scored high risk, which makes these usable as a CI gate; 2 is a usage error.

The graders are implemented twice — stdlib Python for the server and CLI, and a browser port so the hosted site can grade without a backend. Parity tests compare them against shared fixtures, so the same target cannot get a different verdict depending on where you scanned it. Run the suite with python3 -m unittest test_engines.py.

Evidence and export

Each of the four scanners renders a self-contained report card: target, final URL, HTTP status, UTC timestamp, verdict, per-finding evidence, and a provenance strip naming the tool, engine and time — so even a cropped screenshot still identifies itself. The two local utilities have no target to report on, so they produce their own artifacts instead: the CSRF PoC Generator exports the PoC and a Markdown assessment, and the JWT Security Workbench exports a Markdown analysis of the pasted token.

Evidence mode is on by default. Once results render it collapses the page chrome so the whole card fits one viewport and your snipping tool captures it in a single shot.

ExportWhat you get
Print / Save as PDFFull card in a paper layout, colors and PoC overlay preserved
Evidence card (PNG)Tool-specific card drawn from the scan data — no live frame
Copy or download MarkdownPaste-ready metadata, tool-specific context, findings, evidence and recommendations
Copy or download JSONVersioned cyberbuddy-report/v1 envelope for automation and archival
Download CSVSpreadsheet-safe metadata and findings; formula-like evidence is neutralized
Download standalone HTMLScript-free, printable report that opens without CyberBuddy

One honest limitation: a cross-origin iframe cannot be rasterized in JavaScript — canvas pixels would be tainted. So CyberBuddy never asks for screen-capture permission and uses no third-party JavaScript. When the live frame itself is the evidence, use Evidence mode plus your operating system's screenshot tool.

Limits of the hosted build

GitHub Pages serves static files and cannot send response headers. For a product that grades response headers, that has consequences worth stating plainly:

  • The policy ships as a <meta http-equiv="Content-Security-Policy"> on every page, which covers script-src, object-src, base-uri and frame-src.
  • frame-ancestors and X-Frame-Options cannot be delivered that way. A meta CSP ignores frame-ancestors by specification, and XFO is header-only — so the hosted site itself is framable, and scanning it will correctly report missing framing protection.
  • HSTS is header-only too. github.io is preloaded at the domain level, so it is covered in practice, but by nothing in this repo.
  • Consequently the hosted site does not score A against itself, while server.py does (95/100 — the remaining points are the plain-HTTP loopback transport warning). That is a hosting limit, not a scoring bug.
  • robots.txt and .well-known/security.txt only take effect at a domain root, so on a project Pages site they sit under /CyberBuddy/ and crawlers will not read them until this moves to a custom domain.

Only the Clickjacking Validator is permitted to frame arbitrary targets; every other page is frame-src 'none'. If you want the hosted build at full strength, run it behind a host that can send headers, or deploy the optional api/ folder and point API_BASE at it.

What leaves your browser

Full privacy notes →

Scan history and the short-lived header cache stay in this browser's localStorage, expire after 24 hours, and are never uploaded. Published reports are built in CI from a fixed demo list — nothing you type is ever written there. Third-party relays are opt-in, disclose only the hostname, and anything they return is flagged unverified. The hosted fallback also sends that hostname to dns.google for A/AAAA resolution after consent, so NXDOMAIN is reported as unreachable rather than receiving a misleading security grade.

For a scan where nothing leaves your machine at all, run python3 server.py locally. Same graders, same origin, no relays.
